## 핵심 원칙 10개

1. 제출목적·독자·적용기한·행위당시 법령을 먼저 확인한다.
2. 사실 인정, 기억/진술, 추론, 법적 평가, 수사·입증 요청은 구분한다.
3. 원본 파일·원문 인용·페이지·행·타임코드·법률 연혁을 검증한다.
4. 유리한 자료만 집약하지 않고 **불리한 원자료와 최강 반론도 정직하게 검토**한다.
5. `범죄혐의→송치→기소→유죄` 사이 서로 다른 판단 기준을 혼동하지 않는다.
6. 소제목은 판단 질문, 첫 문장은 답 또는 판단해야 할 쟁점을 말하고 근거·제약을 뒤따르게 한다.
7. 그래프와 화살표는 실제 원자료의 연결 관계만 묘사한다. 근거 없는 인과·공모선 금지.
8. AI가 다듬은 법률·판례·사실·금액은 **독립 원문**으로 대조한다.
9. 문서 내용 개선과 DOCX/PDF 렌더·제출형식 검수는 별개 작업으로 평가한다.
10. 원본 보존·비공개·제출 전 최종 인간 승인을 지킨다. **내부 100점은 승소율이 아니다**.

## 산출물과 종료 게이트

`S0~S6` 전략체크, `P0~P8` 수정검수, `ISS→LAW/FACT→EV→ARG→PAR→VIS/ATT` 역추적, 충돌·불리자료 매트릭스, 법령 기준일, 제출형식, 개인정보 보호, PDF 미리보기, diff, 심각오류 0건.

**최종 판정값**: `READY_FOR_HUMAN_REVIEW` / `NEEDS_VERIFICATION` / `SUBMISSION_BLOCKED`. 실제 제출권한과 적법성은 사건별로 확인하고 법률가의 검토를 받는다.

## 패키지 구성의 완결성

이 문서가 단일 기준본이다. 상호 충돌 시 `법령 원문/사건 원본`이 최우선이며, 패키지 내부에서는 **V5 보완 규칙 > 승계한 작성·수정 기본 규칙 > 승계한 세부 명세** 순으로 적용한다. 학술연구는 권고의 근거일 뿐 법령·원증거를 대체하지 않는다.

## 승계한 핵심 작업 규칙

1. **본문 대 후주**: 주장+핵심 인용+정확한 증거 위치는 가깝게, 긴 원본·전사·거래내역은 증거목록과 별첨으로. 유일한 '학술적으로 최적' 법률형식으로 단정하지 말 것.
2. **두괄식**: 독자가 먼저 판단 대상을 알게 하되, 필요한 사전 법리와 근거를 함께 제공하는 *조건부 두괄식*. 결론을 모든 문장 맨 앞에 강요하지 말 것.
3. **문체**: 의미를 유지하면서 명확한 주어·능동 표현·일반어 사용. '변제하지 않았다', '고지하지 않았다' 등 법적 부정 사실은 결코 긍정으로 바꾸지 말 것.
4. **폰트**: 유일한 '최고' 없음. 민사 기본 12pt 이상·법정 여백/줄간격; Windows 호환성 맑은 고딕, 이식성 본고딕, 긴 서술 본명조, 표·디지털 문서 Pretendard 후보. 실제 렌더 비교 후 선택.
5. **법리 검증**: LAW/FACT/EV/ARG/PAR/VIS/ATT ID와 공식법령 시행일·부칙·기한·증거 원문을 연결. AI의 인용문/판례 환각은 별도 원문과 독립 검사.
6. **시각화**: 모든 차트/표/흐름도는 원자료 위치와 단위·미확인 선을 구분. 강조는 문장의 난해함을 구제하지 못함.
7. **토큰 절약**: L0 상시 최소지침, L1 전문 문서, L2 단계별 프롬프트, L3 사건별 증거 인덱스, L4 변경 delta. 고정 prefix 재사용·필요한 원문만 검색하되 최종 제출 전 전체 영향범위 재검증.
8. **AI 변경관리**: P0 동결 → P1 사실 → P2 법리 → P3 반론 → P4 구조 → P5 문체 → P6 인용/시각 → P7 렌더 → P8 독립 감사. 단순 교정은 위험기반 생략 가능하지만 P0·관련 사실검증·P8은 축소 금지.
9. **독자 인용성**: '행위자 + 날짜 + 확인된 행위 + 출처 + 입증의 한계'로 구성. '유죄로 인용하기 좋은 문장'을 생산하느라 무죄추정·입증책임·불리한 사실을 왜곡하지 않는다.
10. **품질 점수**: 작성체계의 정적/동적 소규모 QA 결과와 개별 제출서면의 적법성·사실진위·독해 시험 상태를 **분리**한다. 필요한 데이터가 없으면 NOT_TESTED.

## 0. 사용방법 및 종료 기준

1. **새 문서**: §1 범위 설정 → §2~§9의 기준 적용 → §12 종횡 QA → §13 점수·게이트 → 법률전문가/제출권자의 승인.
2. **기존 문서**: 원본 복제 및 해시 보존 → §9의 P0~P8 → §10 단계별 프롬프트 → §12 QA → §13 평가.
3. 자료 확인 표기는 `VERIFIED / PARTIAL / UNVERIFIED / NOT_APPLICABLE`로 구분한다. 데이터가 없으면 `UNVERIFIED`이고, 증거 없음을 증거 불필요로 바꾸지 않는다. `scripts/strategy_qa.py`의 필드·진단값은 다음과 구별한다.
   - 법령·증거의 `verified`는 불리언이며 `true`여야 통과한다. 불리자료의 `verification_state`는 `VERIFIED_SOURCE`여야 통과한다.
   - `facts.status`는 허용값을 검사하지 않는 메타데이터다. 위 자료 확인 표기를 검사기의 열거값으로 오인하지 않는다.
   - 감사의 `state`: `PASS / FAIL / REVIEW`; `terminal`: 불리언.
   - 변경의 `state`: `OPEN / CLOSED / ROLLED_BACK`; `rollback_state`: `NOT_REQUIRED / PENDING / COMPLETED`. `CLOSED`는 `NOT_REQUIRED`, `ROLLED_BACK`은 `COMPLETED`와 짝을 이룬다.
   - 명령행 진단: `PASS_SYNTHETIC_LINKAGE / FAIL_SYNTHETIC_LINKAGE`. 위 값과 원본·전사 등의 출처 표기는 내부 검사·자료 분류용이다.

   문서 최종 판정은 `READY_FOR_HUMAN_REVIEW / NEEDS_VERIFICATION / SUBMISSION_BLOCKED`만 사용한다.
4. `CRITICAL` 게이트 미통과 때 문서의 디자인 점수가 높더라도 **제출 완료 판정을 금지**한다.
5. 복잡한 사건에서 AI는 자료 검토·비교·구조화의 보조자다. 사실 인정, 법률적 책임 판단 및 제출의 최종 책임 주체를 대체하지 않는다.

**중첩 충돌 해결**: 예를 들어 ‘증거번호 정확성’의 원천 책임은 D02, 본문 링크 책임은 D08, 최종 일치검사 책임은 D12다. 같은 규칙을 세 번 선언하지 않고, ID를 주고받는 인터페이스만 검사한다. ‘메타성 문장 제거’는 D07, 제거 과정에서 의미 변경 검사·승인은 D10이 담당한다.

### 1.1 검증 기본 객체(사건·문서별 SSOT)

ID·연결의 단일 표는 `scripts/strategy_qa.py`의 `SCHEMA`를 따른다. 필수 필드는 비어 있지 않아야 하며 대상 ID가 존재해야 한다.

| 접두어 | 컬렉션 | 의미 | 필수 연결 필드 → 대상 |
|---|---|---|---|
| R | requirements | 요구사항 | issue_ids → ISS |
| ISS | issues | 쟁점 | rule_ids → LAW; fact_ids → FACT; adverse_ids → ADV |
| LAW | laws | 법령·판례 | fact_ids → FACT |
| FACT | facts | 사실명제 | evidence_ids → EV; visual_ids/attachment_ids는 필요 시 VIS/ATT |
| EV | evidence | 증거원본 | visual_ids/attachment_ids는 필요 시 VIS/ATT |
| ARG | arguments | 논증 | evidence_ids → EV; rule_ids → LAW; paragraph_ids → PAR |
| PAR | paragraphs | 문단·문장 | fact_ids → FACT; evidence_ids → EV; adverse_ids → ADV; visual_ids/attachment_ids/change_ids는 선택 |
| VIS | visuals | 표·그림 | change_ids → CHG (선택) |
| ATT | attachments | 별첨 | change_ids → CHG (선택) |
| CHG | changes | 변경 | changed_ids·affected_ids → 모든 유형; qa_ids → QA |
| QA | audits | 감사 | target_ids → 모든 유형 |
| ADV | adverse | 불리자료·반론 | evidence_id → EV |

`CHG.next_change_ids → CHG`는 선택 연결이다. 정방향 검사에서 `ARG.evidence_ids`는 `EV → ARG`로 역전되고, `ISS.fact_ids`, `ARG.rule_ids`, `PAR.fact_ids/evidence_ids/adverse_ids`는 영향 전파용이다. `CHG.changed_ids`, `QA.target_ids`는 대상에서 변경·감사로 연결하며 `CHG.affected_ids`는 영향 범위다. VIS/ATT/CHG/QA 컬렉션은 선택이지만 참조된 ID는 존재해야 한다. 일반 서면의 핵심 추적 종점은 PAR이고, 변경이 있으면 영향 전파·재감사·종료 검사가 적용된다. 독립 QA도 완료된 PASS와 terminal=true가 필요하며 change_revisions의 변경 ID는 실재해야 한다. FACT/EV의 `needs_visual` 또는 `needs_attachment`가 불리언 true면 해당 노드의 visual_ids/attachment_ids가 필수다. ISS/PAR의 불리자료 검토 연결은 유지한다.

사건 데이터의 기준 형식은 `SCHEMA`와 `SCALAR_FIELDS`를 따르는 JSON이다. CSV는 입력 뷰이며 `scripts/csv_to_record.py`로 변환한다. 노드의 미정의 필드는 오류이고 루트 메타데이터는 보존한다. 모든 문자열·검증 플래그는 사용자가 원자료를 확인해 입력하며 가져오기 도구가 빈칸을 추정하지 않는다.
- LAW의 `source`(근거 인용 문자열), `source_location`, `source_excerpt`는 필수이며 source는 발췌에 문자 그대로 존재해야 한다. EV도 source_location/source_excerpt가 필수이며 exact_quote/amount_krw를 적으면 자신의 발췌와 일치해야 한다.
- FACT.text는 참조 EV 발췌에 문자 그대로 있어야 한다. PAR는 draft_anchor(서면 문단 위치), quote, amount_krw 필드를 갖추고 인용·금액이 참조 EV의 값 및 발췌와 일치해야 한다. 금액이 해당하지 않으면 null과 amount_not_applicable_reason을 적되 원문의 금액을 숨길 수 없다. 쉼표로 묶은 숫자도 문자 그대로 비교한다.
- 미해결 항목은 루트 unresolved 문자열 목록에 적는다. 이 목록은 검사 오류를 상쇄하지 않으며, 발췌의 문자 일치가 원본 진정성·법령 적용의 검증을 대신하지 않는다.
- DOCX 검사는 config/style_profile.json을 기준으로 모든 구역·텍스트 run(표·머리말·꼬리말 포함), 사용·설정 스타일을 검사한다. 미사용 비설정 스타일은 목록에 기록한다. common의 머리말·꼬리말·표 최소 글자 크기와 줄간격을 구분하며 위치가 있는 오류는 종료코드에 반영한다. 글꼴 선호 목록은 권고이며 실제 렌더는 별도 검수한다.

서식의 `ISSUE_ID`, `ADVERSE_ID`, `SOURCE_ID`, `제출문장ID`는 각각 ISS, ADV, EV, PAR를 적는 열 이름이며 별도 노드 접두어가 아니다. 요구사항 접두어는 `R`로 쓴다.

- 링크 1개마다 출처·위치·상태와 해당 링크를 만든 주체를 기록한다.
- 한 증거가 여러 요건을 뒷받침할 수 있으므로 `EV : FACT`는 **다대다**를 허용한다. 억지로 분할해서 원본을 훼손하지 않는다.
- `FACT → EV` 연결이 없으면 직접증거가 없다는 의미일 수 있으므로 간접증거·진술·수사요청·미확인으로 정확히 분류한다.
- 검증 가능한 단위를 최소화할수록 추적성은 높아지지만, 실무 운영비용이 과도하면 핵심 문장·증거에 먼저 적용한다.

## 4. 원증거·사실명제 관리 (D02)

### 4.1 증거 등급과 기록

- `EV-ORIGINAL` 실제 원본(메시지 원본·계좌 원본·녹음·계약서 등). 원본이라고 주장하기 전에 취득 경로와 원본성 확인 상태를 표시한다.
- `EV-DERIVED` 캡처·OCR·전사·축약·번역·보정된 이미지. 원본과 대조하고 편집 사실을 표시한다.
- `OWNER-STATEMENT` 당사자 기억·추가 설명. 기억이 강하더라도 객관원본으로 승격하지 않는다.
- `INFERENCE` 검토자가 여러 자료로부터 도출한 가설. 반대 근거와 증명 범위를 기록한다.
- `UNVERIFIED` 출처나 원본 자체를 찾지 못했거나 핵심 정보가 불명확함.

**절대조건**: 발신자·행위자·송금 승인자·수취인·작성자 등 역할을 섞지 않는다. ‘A가 완료 문자를 보냈다’ ≠ ‘A가 돈을 송금했다’ ≠ ‘A가 송금을 승인했다’.

### 4.2 증거 인덱스(표준 열, 내부용)

`EV_ID, 원본파일ID, 출처경로, 작성자/발신자, 발생시각, 문서작성시각, 입수시각, 원본/파생, 해시(가능하면), 페이지/행/시각, 원문, 연결FACT_ID, 증거방향(지지/반박/중립), 확인상태, 진정성/취득방식/증거능력 검토, 공개·제출 여부, 개인정보 처리, 검토자·검토일`.

기술적 SHA/EXIF는 무결성·메타데이터 확인에 도움되지만 그 자체로 법률상 진정성·증거능력을 확정하지 않는다. OCR의 인식 결과나 녹취 전사에서 판독 어려운 부분은 임의 보정하지 않고 원본과 대조한다.

### 4.3 주장별 5단계 질문

1. **원문**: 무엇이 실제 기록돼 있는가? (인용이면 정확히 일치하는가)
2. **맥락**: 앞뒤 대화·동일 거래·작성 경위와 일치하는가?
3. **범위**: 무엇까지 증명하는가? 무엇은 증명하지 못하는가?
4. **반증**: 상대방에게 유리한 다른 기록·설명이 있는가?
5. **용도**: 법률요건·문서 쟁점·추가 수사 요청 중 어디에 사용할 것인가?

## 5. 법리·논리·반론 검증 (D03 + D04)

### 5.1 법리 검증 순서

`절차 유형 → 사건 기준일/적용 법령 → 청구/죄명 → 요건/항변·재항변 → 입증책임/증명 정도 → 필요한 사실 → 실제 증거 → 반대증거 → 제한된 소결`.

- 법률·판례는 국가법령정보센터/공식 판례 원문을 최우선 확인한다. 판례의 사건번호·선고일·판시사항·사실관계·법률상 지위(다수/별개의견 등)를 검증한다.
- 사실의 성립, 진술·추론, 죄명별 구성요건 충족 여부, 증거능력·증명력, 절차상 효과를 섞지 않는다.
- 민사: 청구원인과 항변·재항변의 입증책임 구분, 금액·손해·이자 산식·기산점 확인.
- 형사: 고의·기망·처분행위·피해 등 개별 죄명에 필요한 요건을 범죄별로 조사하되 **일반적인 사기 예시를 다른 죄명에 기계적으로 적용하지 않는다.**
- 검증할 수 없는 판례는 '미검증 인용'으로 표시하고 최종본의 확정적 근거로 사용하지 않는다.

### 5.2 논증의 최소 단위와 반론 시험

`ISS-01 판단할 쟁점 → LAW-01 적용 규범 → FACT-01 직접 확인 사실 → EV-01 원본 위치 → ARG-01 왜 요건에 관련되는가 → ADV-01 가장 강한 다른 설명·반박/인정할 한계 → PAR-01 현 단계 소결`. 반론의 최강 해석·인정할 사실·응답은 ADV의 `strongest_reading`, `admitted_fact`, `response`에 기록한다.

- 논리적 연결은 **필요조건/충분조건**, 시간적 선후/인과, 행위자/수익자, 상관/인과, 가능성/확실성을 구별한다.
- 반론을 허수아비처럼 약하게 만들지 않는다. 가장 강한 유력 설명 1개 이상을 재구성하고 실제 자료로 검토한다. 양면 메시지에 관한 연구가 모든 상황에서 즉각적 반박의 설득상 우위를 입증한 것은 아니므로, 법률적으로 필요한 반박과 심리적 개방성 효과를 혼동하지 않는다.
- 본문에 원인이 없는 법적 수식어(‘명백히 기망’, ‘전부 공모’, ‘당연히 유죄’)는 증거의 한계에 맞춰 완화하거나 삭제한다.
- 독자별 판단 기준에 맞지 않는 문장(경찰에게 판결문식 인정, 검사의 기소 여부를 사전에 확정 등)을 피한다.

### 5.3 바로 인용 가능한 문장 4종(형식 예시, 가상 사실)

1. **사실**: “2025. 3. 4. A가 B에게 ‘입금 완료’라는 문자메시지를 발송한 사실은 원본 메시지에서 확인된다(증거자료 3, 2쪽).”
2. **한계**: “위 메시지는 A의 표현을 확인할 자료이나, 실제 계좌의 입출금 여부나 송금 지시자의 신원을 직접 증명하지는 않는다.”
3. **법률 관련성**: “따라서 실제 지급 여부를 판단하려면 같은 날의 금융거래 기록 및 계좌 명의자에 관한 자료를 대조할 필요가 있다.”
4. **요청**: “신청인은 해당 거래 기록의 확인과 관련자 진술의 대조를 요청한다.”

인용성 테스트: 한 문장만 읽어도 **언제/누가/무엇을/어떤 증거로/어디까지**인지 파악되는가? 법원 판단을 가장한 단정, 핵심 주체 생략, 출처 없는 숫자/판례는 FAIL.

## 6. 의사소통·설득·문체 (D05 + D07)

### 6.1 독자 중심 원칙

- 첫 페이지에서 요청·중심 쟁점·가장 중요한 근거를 찾을 수 있게 한다. **두괄식은 조건부**: 법률개념이 복잡하면 필요한 설명 직후 요지를 다시 강조할 수 있다.
- 중요한 주장은 제목·문단 첫 문장·요약에서 일관된 말로 제시한다. 단 반복은 신규 정보가 있을 때만.
- 독자의 심리적 조작을 목표로 하지 않는다. 핵심 논거의 신뢰성, 공정한 반론처리, 명확한 사건 경위에 집중한다.
- 위협적 언어·인신공격은 법적 설득 대신 저항과 불신을 초래할 수 있다(간접 연구). 확률 수치로 승소·기소 효과를 계산하지 않는다.

### 6.2 문체 결정 규칙

1. **주체+동사**: ‘송금이 이루어졌다’보다 근거가 있을 때 ‘A가 B에게 100원을 송금했다’. 송금자 불명확하면 ‘A 계좌에서 B 계좌로 100원이 이체된 기록이 있다’.
2. **능동형 우선, 법적 의미 보존**: 수동형이 행위자 미상, 사건/결과의 중심일 때는 적절하다.
3. **긍정형 우선, 요건 부정은 보존**: ‘고지하지 않았다’, ‘변제하지 않았다’는 요건일 수 있다. 무조건 긍정으로 바꾸지 않는다.
4. **문장 하나·판단 한 개**: 필요하면 긴 인용문·복합 요건은 분리. 글자수 1개 기준 강제 금지.
5. **원문을 부풀리지 않기**: '진술', '원본 확인', '추정', '의심', '확정'의 표현 강도를 검증 상태에 맞춘다.
6. **인간다운 서면**: 구체적이고 자연스러운 문장, 일관된 존칭·관공서 문체, 인상적인 문장이 아닌 검증 가능한 동사.
7. **메타성 제거**: AI 지시, ‘아래에서 개선하겠습니다’, ‘생성된 초안’, 검토 단계, `TODO`, 숨은 링크·주석, 모델평가 설명이 제출 본문에 들어가지 않도록 한다. 단 법률상 설명이 필요한 작성/검토 경위는 메타로 오인하여 삭제하지 않는다.
8. **정확한 지시어**: ‘위’, ‘그’, ‘해당’은 지시 대상이 멀어지면 구체 명사로 바꾼다.
9. **법률용어**: 공인된 요건명은 유지하면서 옆에서 짧게 풀어 설명. 법률적 의미가 변하는 평이화 금지.

### 6.3 문장 비교

| 피할 표현 | 더 안전한 서술 | 확인사항 |
|---|---|---|
| “누가 보더라도 사기다.” | “A의 설명은 B 자료의 기재와 일치하지 않는다.” | A 설명과 B 원문 확인 |
| “관련 금전이 임의로 인출되었다.” | “○일 계좌거래내역에 ○원이 인출된 기록이 있다.” | 인출 주체·승인자는 별도 검토 |
| “아무런 조치도 하지 않았습니다.” | “○일 기준 신청인이 확인한 기록에는 ○ 조치가 나타나지 않습니다.” | 부재 증명 범위 명시 |
| “이 부분은 절대 하지 않습니다.” | “이 부분은 원자료와 별도로 검토합니다.” | 부정형이 중요한 요건이면 유지 |

## 7. 문서 목차·논증 배열·참고자료 (D06 + D08)

### 7.1 구조의 공통층(한 문단의 모든 층을 강제하는 것이 아님)

`표제 및 자격·절차 → 신청/청구취지 → 핵심 요지(짧게) → 쟁점별 FACT/LAW/EV/반론 → 구체적 결론/요청 → 증거목록/별첨`.

- 짧은 문서: 장황한 목차 대신 2~4개 의미 있는 소제목.
- 긴 문서: 1~2단계 계층형 목차와 자동 페이지, 쟁점에 답하는 제목(‘3. 주장 3’ 지양).
- 소제목 수준과 본문 논증 수준을 일치시키며, 개별 쟁점만 읽어도 판단대상·증거로 이동할 수 있게 한다.
- 불송치 이의신청: **기존 결정 근거 → 다투는 사실 또는 판단 → 원자료/반증 → 누락 수사 → 절차상 적절한 요청**.
- 민사 소장·준비서면: **청구/항변의 범위 → 요건별 사실 → 증거 → 항변·재항변 → 계산표 → 결론**. 준비서면의 불필요한 반복과 분량 제한 점검.

### 7.2 본문/각주/증거목록/부록 위치 결정

| 내용 | 원칙적 위치 | 예외·리스크 |
|---|---|---|
| 결론, 판단 대상, 핵심 사실 | 본문 | 법적 설명이 필요하면 소결을 재진술 |
| 핵심 근거의 짧은 인용 및 pinpoint | 해당 주장과 가까운 본문 | 맥락을 삭제한 발췌 금지 |
| 판례·조문 | 필요할 때 본문과 함께 정확한 원문 출처 | 장문의 판례 전문은 별첨/각주 |
| 제한적인 표/사진/문자 발췌 | 본문 또는 바로 인접한 페이지 | 확대·크롭은 편집 표시 및 원본 링크 |
| 장문 녹취·거래내역·전체 계약서 | 별첨·증거목록 | 본문에서 정확한 페이지/시각으로 접근 |
| 학술적 참고문헌(이 가이드용) | 문서 말미 | 실제 법률서면에는 필요할 때에만 |

**양방향 추적 규칙**: `본문 FACT-ID → 증거 EV-ID/페이지 → 원본`이 존재하고 반대로 `첨부 EV-ID → 적어도 하나의 사용처/제출 목적`이 존재해야 한다. 참고·백업용 첨부는 ‘제출 목적=참고/보존’으로 분류해 무의미한 연결을 강요하지 않는다.

### 7.3 중복 방지와 완전성의 균형

- 같은 사건 사실이 여러 법률요건에 적용되면 한 곳에서 상세 서술하고 다른 곳에서는 `§X 및 증 제Y호증 참조`로 연결한다.
- 배경사실 반복을 줄여도 반대증거의 법적 관련성이나 사건별 인과관계를 삭제하지 않는다.
- ‘원고/피고’, ‘신청인/피신청인’, ‘고소인/피고소인’은 문서의 절차에 맞추어 일관 사용한다.
- 민사에서 형사 확정판결 등을 원용할 때 그 효과와 범위는 별도 법리 검토하며 다른 사건의 사실인정을 그대로 자동 이식하지 않는다.

## 8. 시각·표·다이어그램 (D09)

| 질문 | 최적 후보 | 점검 항목 |
|---|---|---|
| 일자·사건 순서가 중요한가? | 연표 | 실제 발생일 vs 문서 작성일, 증거 ID |
| 인물/법인/계좌/지시 흐름이 복잡한가? | 흐름도·관계도 | 각 화살표의 원본 근거; 추정 점선+문자라벨 |
| 죄명 요건·민사 요건이 여러 개인가? | 요건–사실–증거 매트릭스 | 지지·반박·공백의 세 칸 |
| 정확한 금액·날짜·계산식이 중요한가? | 숫자 정렬 표 | 단위, 소수점·반올림, 기간·기준일, 합계 |
| 동종 시간 자료로 추세를 보여야 하는가? | 막대/선 차트 | 원자료, 축의 0·절단표시, 누락값 |
| 핵심 문구가 짧고 맥락 제한이 가능한가? | 원문 발췌 | 문맥·생략표시·원본 페이지 |

**강조 정책**: 우선 문장을 쉽게 쓰고 그다음 소제목/굵기. 본문 전체 볼드 금지. 밑줄은 주의해서 사용. 색은 적게, 검정·회색 기반. 색상만으로 상태 구분 금지. 아이콘·레이블을 병행하고 흑백 인쇄 테스트. 표 안 글씨를 지나치게 줄여 분량을 맞추지 않는다. 이미지의 연결선·텍스트·표 셀은 원증거와 대조한다.

**표 정적 QA**: 제목/단위/기준일/원자료/열 합계/행 라벨/잘림/페이지 분할/고아행/중복값/공백값/같은 열의 자료형·정렬/인쇄 대비를 확인한다.

## 9. 기존 문서 수정: 9개 단계, P0~P8과 1:1 대응 (D10)

핵심은 **진단과 수정, 수정과 검증, 검증과 승인**을 분리하는 것이다. 9단계가 통계적으로 최적이라는 실증을 주장하지 않는다.

| 단계 | 단일 소유 목적 | 산출물·변경권한 | 다음 단계 진입 조건 |
|---|---|---|---|
| P0 동결·범위 | 문서·첨부 식별, 버전/해시, 제출조건 | 원본·작업본·목록·금지변경 / 무수정 | 원본 보존 확인 |
| P1 추출·진단 | FACT/EV/LAW/날짜/인명/금액/문단ID 추출 | 원문 인덱스·미확인 목록 / 무수정 | 누락·오독 목록 확인 |
| P2 법리 감사 | 절차, 요건, 법령·판례 원문, 시점 검토 | 요건 매트릭스 / 무수정 | 치명적 법리 오류 식별 |
| P3 적대적 반론 | 불리한 사실·대안 설명·증거능력·논리 공백 | 반론 목록·보완 우선순위 / 무수정 | 강한 반론을 일부러 누락하지 않음 |
| P4 구조 설계 | 목차·분량·문단 전후 매핑 | 최소 변경안/재배치안 / 계획만 | 소유자·검토자 승인 범위 획득 |
| P5 내용·문체 교정 | 승인된 범위의 사실 불변형 문장·문단 수정 | 변경된 텍스트·CHG diff / 제한 수정 | 의미변경·누락 전수 검토 |
| P6 참조·시각화 | pinpoint·증거목록·표/그림 연결 | 인용/별첨 매트릭스·VIS / 검증된 변경만 | 원본/원문 인용 일치 |
| P7 렌더·보안 | DOCX/HWP/PDF 생성, 폰트·쪽·마스킹 | 제출 후보 파일·출력 QA / 형식변경 | 인쇄·전자제출 테스트 통과 |
| P8 독립 최종감사 | 원본–완성본·법령·증거·렌더 대조 | 항목별 QA·승인 로그·§13.2 최종 판정 | CRITICAL=0, 미확인 핵심 사항 해결/명시 |

### 9.1 재귀 루프(역방향 트리거)

- P8에서 원문 왜곡 발견 → 해당 P5/6 변경 롤백 → P1 증거 인덱스 검토 → 다시 P8.
- P6에서 미확인 증거 발견 → P1/2/3으로 되돌리고 해당 주장 철회/보류 또는 보강 필요 표시.
- P7에서 페이지/표/인용 위치 변경 → P6 참조번호 갱신 → P8 독립 대조.
- P4의 목차 변경으로 쟁점이 사라짐 → P3 반론·P2 요건 누락 재확인.
- P2에서 적용법 시점 오류 발견 → P0 절차 파라미터 재설정 → P2 이후 재실행.
- 중요 변경은 `CHG_ID, 전원문, 신원문, 이유, 출처, 영향범위, 검증결과, 승인자, 승인일, 롤백버전`으로 남긴다.

### 10.0 공통 시스템 규칙(매 단계에 선행)

```text
이번 단계에 명시되지 않은 작업은 하지 않는다. 변경이 필요한 단계는 diff/근거/승인여부 기록.
출력: 범위 → 확인내용과 정확한 원문위치 → 미확인/반론 → 영향범위 → 항목별 검사 결과 → 최종 판정 `READY_FOR_HUMAN_REVIEW / NEEDS_VERIFICATION / SUBMISSION_BLOCKED`.
```

### P0 — 동결/범위

```text
[단계 P0] 문서와 증거를 수정하지 마라. 문서 종류·제출기관·사건 기준일·통지/접수일·최신 제출기한·법령 적용일, 파일명·버전·해시, 금지변경 목록, 결측 자료를 목록화하라. 원본이 보존되지 않았으면 중단하라. 산출물: SOURCE_MANIFEST와 작업 사양.
```

### P1 — 원문/증거 추출
```text
[단계 P1] 문단마다 PAR-ID, 주장마다 FACT-ID, 증거마다 EV-ID를 부여한다. 날짜·금액·인물·지위·인용문·증거번호·출처 위치를 원문 그대로 추출한다. 원본·전사·진술·추론·미확인을 구분하고 중복/모순/누락을 기록한다. 문서 수정 금지. 산출물: FACT-EV INDEX.
```

### P2 — 법리 감사
```text
[단계 P2] 절차·법률문제별 요건/항변·재항변/입증책임·증명정도, 행위시점 및 제출시점의 적용법·부칙·판례 원문을 대조하라. 조문·판례마다 정확한 URL과 문서 부분을 기입하라. 검증되지 않은 판례를 생성하거나 확정적으로 인용하지 마라. 산출물: LAW-FACT MAP과 적용시점 검증표. 본문 수정 금지.
```

```text
[단계 P4] 문장을 고치지 말고 간결한 최소변경안과 필요시 전면재배치안을 작성하라. 각 제목을 쟁점/법률요건/독자의 질문에 연결하고 기존 PAR-ID와 새 배치를 전후 매핑하라. 중복은 참조로 대체하되, 불리한 자료와 공통증거의 역할을 지우지 마라. 산출물: 승인 대상 STRUCTURE PLAN.
```

### P6 — 인용/시각 검증
```text

```

### P7 — 렌더/배포 검증
```text
[단계 P7] 최신 제출기관 기준에 맞춰 문서 형식·서명·개인정보 마스킹·첨부목록·분량을 확인한다. 실제 DOCX/HWP→PDF를 렌더링해 전체 페이지에서 폰트 대체, 12pt/줄간격(민사 해당 시), 표 잘림, 고아행, 번호, 흑백 인쇄, 이미지 원본과의 일치를 검사한다. 변환 결과를 직접 보지 못한 항목은 검증완료로 선언하지 마라.
```

### P8 — 독립 최종 검증
```text

```

## 12. 종·횡·상호 재귀 MECE QA (D12)

### 12.1 세로 검증(위→아래 / 아래→위)

**정방향**: 제출 목적·절차/적용법 → 쟁점 → 법률요건 → 주장할 사실 → 실제 증거 → 논증·반론 → 문단·표 → 제출결론.

**역방향**: 모든 결론과 핵심 문장/수치/선·화살표 → 원본 증거 및 관련 법률까지 추적. 중간에 `UNVERIFIED`가 있으면 명확히 표시하거나 수정·삭제.

**세로 테스트**: (V1) 핵심 쟁점별 요건 충족/공백 표시, (V2) 주장별 출처, (V3) 결론별 법적 관련성, (V4) 각 상위 목차가 하위 문단으로 설명, (V5) 문단·문장과 원문 의미 동일.

### 12.2 가로 검증(동일 층 교차점검)

- (H1) 사건 전체의 인명·직함·당사자 호칭 일치.
- (H2) 일자·금액·계좌·산식·원자료 수치가 장/본문/표/별첨에 걸쳐 일치.
- (H3) 법령·판례·적용시점이 다른 장에서 다르게 쓰이지 않음.
- (H4) 같은 사실에 다른 추론·확정 등급을 붙이지 않음.
- (H5) 본문 증거번호·별첨·목차·페이지·링크의 양방향 일치.
- (H6) 동일 쟁점의 중복 서술이 서로 다른 법적 의미를 만들지 않음.
- (H7) 반대증거/의문점이 유리한 섹션으로만 편향 배치되지 않음.
- (H8) 표·그림의 실제 값·노드·선이 본문·원본과 일치.

### 12.3 상호 재귀적 교차점검

- **거시 → 미시**: D01~D12 영역별 누락 → 장/절 → 문단/문장 → 사실/증거 → 단어·표 셀 → 렌더까지 내려간다.
- **미시 → 거시**: 단어·수치/증거 수정의 영향이 법률요건·주장·목차·결론/요청에 미치는 변화를 다시 올려 확인한다.
- **교차 영향**: 예를 들어 금액 오류 발견은 D02(원자료)→D04(논증)→D07(본문)→D09(표)→D08(첨부)→D12(감사)로 다시 전파한다.
- **고정점 조건**: 검토 회차에서 신규 CRITICAL/HIGH가 발생하지 않고, 변경이 승인된 범위 안에 있으며, 핵심 링크가 양방향 확인되면 종료한다. 단 정적 설계의 고정점은 사실·법률의 절대적 진실을 보증하지 않는다.
- **중단/롤백**: 법리 시점 오류, 원증거 왜곡, 필수 서식 불합치, 미승인 핵심 사실변경, 보안 유출 우려 발생 시 즉시 해당 변경 중단, 이전 안전 버전으로 복귀.

### 12.4 독립감사의 독립성

P8의 ‘독립’은 P5 초안 작성자의 자체 칭찬이나 같은 입력의 재출력이 아니라, 원문·원증거·법령 원문과 대조하여 오류를 찾는 **별도 검토 역할**을 뜻한다. 가능하면 다른 담당자/모델/검토 흐름을 사용하되, 서로 다른 모델끼리 합의했다고 진실이 입증되는 것은 아니다. 공식 원문 확인·당사자 검토·권한 있는 법률전문가 검토가 최종 단계다.

### 12.5 증빙 없는 점수 금지

점수에 증거를 연결한다: `평가항목 → 관측한 산출물·행/문단/파일 → PASS/REVIEW/FAIL → 계산`. 실제 사건 파일·출력 PDF 없이 문서의 **사실 정확성이나 제출 적합성** 점수를 매기지 않는다. 이 가이드의 점수는 어디까지나 **체계 설계 완결도**다.

### 16.4 인용 방식 비교 연구의 빈틈 명시

본문 인용 vs 각주 vs 후주 vs 별첨에 대해 한국 민사·형사 실무자의 실제 사건 판단률을 직접 비교한 인과실험을 이 조사에서 확립하지 못했다. 따라서 본문 `핵심 주장+정확한 증거위치` / 별첨 `완전한 원본` 방식은 **인지부하/정보 탐색 원리에 기초한 재현 가능한 실무 기본값**이지 절대적인 최적해는 아니다. 특정 접수기관의 형식이 우선한다.

## 17. 정적·동적 테스트 명세 (가상 사례를 통한 회귀 테스트)

### 17.1 테스트 데이터는 100% 가상·비밀정보 없음

가상 사건의 예시: '가상회사 주식회사 새별', '가상의 담당자 갑', '2026-01-12 계약', '1,000,000원 송금', '2026-01-15 문자', '첨부 E01/E02'. 이 자료는 실제 사건을 암시하지 않으며 제출 불가 워터마크를 붙인다.

검증 객체와 연결은 §1.1의 단일 ID 표를 따른다. 객체의 존재·연결 및 상태전이를 검사한다. 도식은 증거가 없는 선을 생성하면 실패해야 한다. 강한 반론을 삭제하면 실패해야 한다.

### 17.2 테스트 유형과 기대 결과

| 테스트 ID | 입력 | 예상 | 품질 게이트 |
|---|---|---|---|
| T01 | 완결된 사실·증거 연결 | PASS | V1~V5 |
| T02 | 동일 FACT 금액이 장/표에서 다름 | FAIL | H2 |
| T03 | 핵심 주장 원증거 링크 유실 | FAIL | V2/G4 |
| T04 | 반론이 이유 없이 제거됨 | FAIL | H7 |
| T05 | 법률 인용이 원문 확인 없이 VERIFIED | FAIL | G3 |
| T06 | 수정 시 인용문이 한 글자 변경됨 | FAIL | G2/P5 |
| T07 | 시각화 화살표 출처가 공란 | FAIL | H8 |
| T08 | PDF 출력 설정 A4/여백/12pt/1.5줄 | PASS(실측값) | P7 |
| T09 | 흑백 출력 대비·한글 대체·표 잘림 | PASS/REVIEW(시각) | P7 |
| T10 | Windows/HWP 설치·실제 사용자 PDF | NOT_TESTED | D11 |
| T11 | 경찰/검사/법관 사용자 검토·인용성 실험 | NOT_TESTED | D05 |

표의 예상값은 항목별 시험 진단이며 최종 판정값이 아니다. T01~T07 중 구현된 인용·금액·연결 검사는 `scripts/legal_qa.py`와 `scripts/strategy_qa.py` 및 관련 단위시험으로 실행한다. 자동화되지 않은 부분은 사람이 확인한다. T08~T09는 가상 DOCX→PDF로 검증한다. **T10~T11 미실시 사실을 ‘PASS’로 바꾸지 않는다.**

### 17.3 독자 가독성·인용성 실제 실험 프로토콜

- 모집: 경찰/검사 실무 경력자 또는 법률전문가 (가능하면 서로 독립된 최소 3인, 외부 검증 시 표본수 계획 별도).
- 가림: 작성자·AI 여부·원본 정체 등 평가에 불필요한 정보 제거, 민감 사건은 허가받은 보안 환경에서만.
- A/B 비교: 동일 사실·동일 법률·동일 증거를 가진 V2/개선본을 문서 형식만 달리 제시. 순서와 배치의 효과를 조정.
- 측정: 정확한 사실 찾기 시간, 주장의 법적 요소 인식, 인용 가능한 문장 개수, 오해·추론 오류, 출처 재탐색 클릭/시간.
- 지표: 정답률, 근거 추적 성공률, 오해율. 사전에 채점자와 목표 기준 합의.
- 결과는 실제 실험 후에만 숫자를 보고하며, 이 프로토콜만으로 인간 독자 효과를 입증하지 않는다.

## 18. 재귀 MECE 검증의 종료조건을 테스트 가능한 명세로 고정

### 18.1 전체 요구사항 테스트 (22개)

각 사용자 요구 R01~R22는 **정의→위치→담당자→프롬프트→검증조건→증빙→상태**가 모두 있어야 ‘구조적으로 완결’이다. 실제 실행 상태는 별도 필드다. 미해결 항목이 존재하는 경우 ‘미해결이 드러난 상태’는 *명세 완결*에 포함될 수 있지만 *사건 검증완료*로 볼 수 없다.

### 18.2 수직·수평 5×8 교차검증

- V1~V5: 접수 목적에서 법적 요건과 원증거·본문 문장까지 내려가고, 본문에서 역으로 법률·증거에 올라가는 검사.
- H1~H8: 각 항목에 인명·일자·금액·법률시점·증거번호·시각자료의 일관성을 가로로 확인.
- 교차점이 의미 없는 경우 `N/A+사유`; 충돌이 있는 경우 `FAIL + 원인 + 복구단계(P0~P8)`를 기록.
- 최소 1회 역방향 **반례 탐색**을 실행(최강 반론/허위 사실·법령/인용 깨짐 테스트).

### 18.3 파일 무결성 / 재실행

- 원본 SHA-256, 작업본 SHA-256, 산출물 SHA-256을 각각 별도로 기록한다.
- 파일 크기·페이지수·문단·표·증거번호 개수의 전후 차이를 대조한다.
- 외부 변환·OCR/AI에서 생성된 파생물은 원본과 구분하고 원본을 수정하지 않는다.
- 회귀 테스트 실패 시 문제 있는 단계로 롤백하고 관련 V/H 검사와 P8 최종감사를 다시 수행한다.

## 19. 설치·운영·재현성 (별도 SSOT)

Windows/PowerShell 전용 단계별 설치법, 도구 기능·한계, 설치·검증·문제 해결 명령어는 `docs/04_도구_설치_설정_사용법.md`와 `config/tool_catalog.json`을 따른다. `scripts/install_windows.ps1`은 **기본 Preview 모드**이며 `-Apply`를 명시했을 때만 설치를 시도하도록 설계했다. 설치하기 전에 조직 보안정책과 기존 Python/Node 버전을 점검한다.

실제 운영 정책: 기존 저장소의 Python, Node, 가상환경을 훼손하지 않는다. 사전에 패키지 목록과 충돌을 확인하고 프로젝트 전용 `.venv`에서 실행한다. 승인되지 않은 외부 API로 사건 자료를 전송하지 않는다.

## 20. 점수와 사건별 검증의 구분

구 수기 루브릭과 단계 등급은 폐기했다. 현재 점수는 `docs/18_상호재귀_MECE_종횡감사_20261107.md`의 동결 루브릭으로 `python scripts/score.py`가 계산하며, 실제 실행값은 `qa/SCORE_HISTORY.md`에 기록한다.

구조 점수와 실제 검증완료는 별개다. Windows 현장 검증, 전문 독자 시험, 실제 사건 자료 검증, 모든 문헌 전문 방법론 검토는 수행 증빙이 없으면 `NOT_TESTED`로 남긴다. 최종 판정은 §13.2의 `READY_FOR_HUMAN_REVIEW / NEEDS_VERIFICATION / SUBMISSION_BLOCKED`만 사용하며, 점수만으로 제출 적합성을 인정하지 않는다. 사건별 법률가 검토와 제출 책임자의 승인이 필요하다.
